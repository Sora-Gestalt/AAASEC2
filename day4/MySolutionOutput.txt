**Code Review Note (style + correctness)**

- **Logic works but the implementation is convoluted**: Building an array of “conditions + messages” inside a nested list comprehension (`return [rule for rule in [ ... ] if rule]`) is harder to read than a straightforward set of `if` statements.
- **Potential false positives / brittle matching**:
  - `"eval(" in code` and `"exec(" in code` can match comments/strings and miss cases with whitespace/newlines (e.g., `eval ( ...`).
  - `"secret" in code.lower()` is very broad—will flag benign words like `secretary`, `consent_secret_flag`, etc.
  - `"subprocess" in code` doesn’t catch shell execution done through other modules (`os.system`, `popen`, `shlex` usage, etc.).
- **Message mapping is implicit**: The rules are expressed as tuples like `condition and "message"`. This is clever, but obscures intent. Explicitness would improve maintainability.
- **Return type and naming**: Consider naming the function `review_code` (or similar) and documenting what inputs it expects (source code as a string) and what it returns (list of finding strings).

**Suggested rewrite (clearer + easier to extend):**
```python
def review(code: str) -> list[str]:
    findings = []

    if "eval(" in code:
        findings.append("Critical: Avoid eval()")

    if "exec(" in code:
        findings.append("Critical: Avoid exec()")

    if "subprocess" in code:
        findings.append("Warning: Audit shell execution")

    if "secret" in code.lower():
        findings.append("Warning: Possible hardcoded secret")

    return findings
```
